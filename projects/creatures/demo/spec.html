Digital Creatures specification

This project is to be a small playground for playing with interacting populations with a graphical display. The graphics should be simple but neat and appealing, primarily block based and simple forms. The will be 3D, with the camera start position looking down onto the whole plane from an isometric viewpoint.

There should be a ground plane populated by animated 3D actors that move around just above the ground. Each actor must turn to face its direction of travel.

Load one hundred thirty-one creatures from genuine game-model bundles and freely reusable animated-asset collections. The Menu project's floaty2 desktop pet supplies nine UFO:AI actors: Taman, Ortnok, Shevaar, Bloodspider, Hovernet, Alien Tank, male PHALANX soldier, female PHALANX soldier, and civilian. Fourteen more animated UFO:AI actors from Menu's pinned source catalogue join them: Taman variants B, C, and D; Taman in light and medium armour; Ortnok variants B and C; Ortnok in light and medium armour; Shevaar variants B and C; Advanced Bloodspider; Advanced Hovernet; and Fish. The same catalogue supplies the Egoboo Bat, Cockatrice, Crab, and Minotore plus Sauerbraten's Hellpig. Twenty-four more models from the pinned Egoboo collection join them: Cobol, Demon, Fire Lizard, Grub Bug, Lumpkin, Trog, Spider, Pit Cobra, Sand Troll, Jelly, Ghoul, Nautilus, Eyeball, Mimic, Mosquito, Scatterbrain, Trorc, Vampyre, Animated Mace, Carpet Mimic, Mephit, Rust Eater, Varguile, and Zombi. Sixteen CC0 glTF actors from Quaternius' Ultimate Monsters collection add Blue Demon, Bunny, Cactoro, Dino, Frog, Mushroom King, Yeti, Cat, Chicken, Dog, Green Blob, Evolved Mushnub, Wizard, Evolved Armabee, Dragon, and Squidle. Twenty-nine more glTF actors from the same collection add Monkroose, two Ninjas, three Orcs, two Tribals, Blob Alien, Blob Birb, Blob Cactoro, Blob Fish, Green Spiky Blob, Mushnub, Blob Pigeon, Pink Blob, Blob Yeti, Alpaking, Evolved Alpaking, Armabee, Evolved Dragon, Ghost, Skull Ghost, Glub, Evolved Glub, Goleling, Evolved Goleling, Hywirl, and Flying Pigeon. Four original FBX bundles from that collection add Alien, Birb, Demon, and Fish with their shared texture atlas. The Khronos glTF Sample Assets Fox adds one CC0/CC BY 4.0 actor. KayKit's CC0 character packs add Barbarian, Knight, Mage, Rogue, Hooded Rogue, Skeleton Mage, Skeleton Minion, Skeleton Rogue, and Skeleton Warrior. The CC0 RobotExpressive model from the three.js examples adds one Quaternius robot. Seven OpenZ robot classes and twelve wildlife actors, including both raptor skins, use the original game's movement and idle animation data. Have them randomly pick a place to move to, then move to it over the course of a few seconds.

The camera uses RTS controls. Left or middle click and drag must raycast onto the ground so the selected ground point stays under the pointer while the map slides. Right click and drag must orbit horizontally and tilt vertically around the current ground target. The tilt is limited to 15-75 degrees above the ground so the camera cannot flip or pass through the plane. The scroll wheel must zoom toward the ground point under the pointer, with an 8-170 world-unit distance limit. The camera target stays within the 140-by-140 ground plane. Pointer capture must keep an active drag working when the pointer leaves the canvas, and the browser context menu must not interrupt right-button orbiting.

Animated Creature Models

  • Load each original MD2 body and diffuse skin. Read UFO:AI animation tables and separate head tag_head attachments, Egoboo animation ranges from the MD2 frame-name prefixes, and Hellpig animation ranges from the md2-config.txt web copy of Sauerbraten's original md2.cfg; retain the original beside it for provenance because the public host rejects .cfg requests.
  • Load glTF 2.0 JSON and binary actors with their embedded skeletal rigs, materials, textures, and named animation clips. Clone each skinned hierarchy independently and cross-fade between its configured movement and idle clips.
  • The OpenZ collection browser loads one model at a time. It includes the nineteen simulation actors and all 323 FBX and GLB source files from release 1.5. The six motion-only files display their skeletons. Each original can be downloaded from the viewer.
  • Load original FBX actors with their skeletal rigs, named animation clips, and shared texture atlas. Clone each skinned hierarchy independently and normalize it with the same movement and idle contract as the glTF actors.
  • Keep only the configured running and idle clips in the KayKit and RobotExpressive web copies, losslessly resample them, prune unused data, and quantize uncompressed vertex attributes so the ten actors add less than three megabytes of model data.
  • Demand-load model bundles through two concurrent workers instead of requesting the entire collection at once. Interleave the source collections, spawn each creature immediately after its bundle validates, and yield between bundles so the simulation stays responsive while loading continues.
  • Retry transient HTTP and network failures up to three total attempts with exponential backoff. A permanent model failure must not remove creatures that already loaded or prevent later bundles from loading; show running and failed counts and log the detailed failure without substituting invented geometry.
  • Give local JavaScript module URLs a shared release-version query so browsers do not retain obsolete loader modules under the public host's month-long JavaScript cache. Bump every local module query together whenever the demo's JavaScript changes.
  • Use the actor's configured walking animation while it moves and its configured standing animation while it waits.
  • Demon, Grub Bug, Jelly, Ghoul, Eyeball, Mosquito, Scatterbrain, Animated Mace, Mephit, and Varguile use their native DA animation loops, slowed while waiting. Carpet Mimic and Zombi use WA movement and DA idle frames; the remaining additional actors use WB movement and DA idle frames.
  • Interpolate the compressed MD2 vertex frames and head attachment transforms, updating rendered geometry at 30 animation steps per second.
  • Normalize each actor to an appropriate world height while preserving its original proportions; use a model-specific collision radius and carry blocks above its head or body.
  • Reject malformed or missing model, animation, tag, skin, glTF scene, or skeletal clip data and show a visible loading failure instead of substituting invented geometry.
  • Keep each bundle's original license and pinned-source provenance receipt beside the web assets, credit Hellpig creator Psionic, and link to those records from the demo.

Scenery Models

  • Place forty-two CC0 buildings and structures from KayKit's Medieval Hexagon Pack around the outer edge of the ground. The original blue castle, church, tavern, two homes, market, blacksmith, barracks, archery range, lumbermill, windmill, watermill, mine, and well remain; blue towers, a complete red village and tower set, bridges, a ruin, grain store, scaffolding, and a stage form a larger outer settlement.
  • Place two hundred two natural scenery objects from fifty-three CC0 Kenney Nature Kit models: deciduous, autumn, palm, and pine trees; cacti; bushes; rocks; grass; flowers; logs; mushrooms; crops; campfires; tents; canoes; stumps; and statues. Together with the buildings, the scene contains two hundred forty-four static scenery objects loaded from ninety-five assets.
  • Keep the central forty-by-forty movement area open. Buildings and large scenery remain outside it so the existing creatures and block tasks do not require building collision or pathfinding.
  • Normalize each scenery model to its configured world height, rest it on the ground, preserve its proportions, and enable shadows on its renderable meshes.
  • Demand-load scenery through two concurrent workers, place every model's configured instances as soon as that asset validates, and yield between assets so creatures and camera controls remain responsive.
  • Retry transient HTTP and network failures up to three total attempts with exponential backoff. A permanent scenery failure must not prevent other assets or creatures from loading; show asset, placement, and failure counts and log detailed failures.
  • Keep the original license and source receipt beside each web asset collection and link those records from the credits page.

VR Support

The project now includes full WebXR support for Meta Quest and other VR headsets:

Setup Requirements

HTTPS Requirement: WebXR requires secure contexts (HTTPS) to function. For local development:

  • Self-signed SSL certificates (cert.pem and key.pem) are generated using OpenSSL
  • HTTPS server runs on port 8443
  • Users must accept the certificate warning in their VR browser

Server Setup:

  • Node.js HTTPS server (server.js) serves the application
  • Automatically serves static files with correct MIME types
  • Helper script (start-vr.sh) displays local IP for easy headset connection

VR Features

WebXR Integration:

  • VR button automatically appears when headset is connected
  • Renderer uses renderer.xr.enabled = true for WebXR support
  • Animation loop uses renderer.setAnimationLoop() instead of requestAnimationFrame() for VR compatibility

VR Controllers:

  • Two controller inputs supported (left and right hand)
  • Visual representation with red spheres at controller positions
  • White lines extend from controllers showing pointing direction (5 units long)
  • Controllers support select events (trigger button) and squeeze events (grip button)
  • Both controllers have identical control schemes

Interaction System:

  • Trigger (select): Point controller at blocks and pull trigger to pick up
    • If pointing at a block: Pick up and carry the block
    • If pointing at empty space: Enter camera pan mode (non-VR browser mode only)
    • Release trigger to drop block at controller position
  • Grip (squeeze): Hold to rotate camera by moving controller horizontally (non-VR browser mode only)
  • Raycasting from controller determines which block is targeted
  • Only available (not carried, not eaten, not flying) blocks can be picked up
  • Picked up blocks follow controller position in real-time
  • Players can interact with the same blocks the creatures are using

Camera Behavior:

  • Desktop camera controls (pan, rotate, zoom) disabled when in full VR presenting mode
  • VR headset position and rotation control the camera directly in VR mode
  • Player can physically walk around the scene using VR room-scale tracking
  • Scene remains at ground level, easily viewable from standing position

VR Locomotion (Full VR Mode):

  • Thumbstick movement: Enabled when in VR presenting mode (after clicking "Enter VR")
    • Forward/backward: Push thumbstick up/down to move in the direction you're looking
    • Strafe left/right: Push thumbstick left/right to move sideways
    • Movement follows camera (head) direction but stays locked to ground plane
    • Movement speed: 0.1 units per frame
    • Dead zone of 0.1 prevents controller drift
    • Both controllers provide identical locomotion controls
    • Allows smooth navigation around the scene without physical movement

Non-VR Browser Mode Controls (VR headset browser, not in VR session):

  • Thumbstick:
    • Left/right: Rotate camera around scene
    • Up/down: Zoom in/out
  • Trigger drag: Pan camera when pointing at empty space
  • Grip drag: Rotate camera by moving controller horizontally
  • These controls allow navigation before entering full VR mode

Task System

The simulation now includes an experimental task system that allows creatures to perform work:

Architecture

Task Manager: Central system that manages all tasks and assigns them to available creatures

  • Maintains a queue of pending tasks
  • Tracks which creatures are available vs busy
  • Automatically assigns tasks to random available creatures
  • Removes completed tasks from the queue

Task: Represents a unit of work with type and associated data

  • Type: Category of task (e.g., 'move_block')
  • Data: Task-specific information (target object, locations, etc.)
  • Assignment tracking: Which creature is assigned and completion status

Creature Task States: Creatures transition through states when executing tasks

  • idle: No task, wandering randomly
  • moving_to_pickup: Moving towards object to pick up (continuously follows block position)
  • picking_up: Brief pause while picking up object
  • carrying: Moving to drop location while carrying object
  • dropping: Brief pause while placing object
  • eating: Attempting to eat the dropped block for 5 seconds
  • Returns to idle after eating completes or is interrupted

Current Implementation

Movable Blocks: Multiple brown blocks that creatures can pick up and relocate

  • Initially 8 blocks spawn at random locations
  • Each block can be carried by one creature at a time
  • Follows creature position when being carried (floating above their head)
  • Dropped at random locations around the map
  • Block list can grow (from emitter) and shrink (from eating) dynamically
  • Blocks can be in flying state with physics-based trajectory

Block Emitter: A fountain structure that periodically launches new blocks

  • Gray cylindrical fountain with a nozzle at position (-15, -15)
  • Launches blocks every 10-25 seconds (random interval)
  • Blocks are fired into the air with a ballistic trajectory
  • Flight time of 1.5-2 seconds with realistic physics (gravity)
  • Blocks spin while airborne for visual effect
  • Landing range of up to 25 units from fountain
  • Upon landing, blocks become available for creature interaction
  • Continuously replenishes the block supply in the world

Task Generation: Block movement tasks are created periodically

  • Random intervals of 3-10 seconds
  • Picks a random available block (not being carried or eaten)
  • Task assigns a random creature to pick up the chosen block
  • Creature picks a random drop location upon pickup
  • Multiple tasks can target different blocks simultaneously

Chase Behavior: Multiple creatures can compete for the same block

  • When multiple creatures are assigned to move the same block, they chase it
  • Creatures continuously update their target to follow the block's current position
  • If one creature picks up the block, other assigned creatures will chase the carrier
  • When the carrier drops the block, nearby pursuing creatures can steal it
  • Creates emergent "hot potato" gameplay with creatures chasing each other

Eating Behavior: After dropping a block, creatures attempt to eat it

  • Upon dropping the block, the creature enters an "eating" state
  • Creature backs away 1.5 units and faces the block (visual improvement and accessibility)
  • Eating takes 5 seconds to complete
  • If another creature picks up the block during eating, the eating is cancelled
  • The interrupted creature returns to idle wandering
  • If eating completes successfully, the block disappears permanently
  • The block is removed from the world and the blocks array shrinks
  • The backup behavior gives other creatures easier access to steal the block
  • With multiple blocks, creates distributed competition across the map
  • As blocks are eaten, competition intensifies over remaining blocks
  • Creates dynamic competition where creatures must defend their meal

Future Extensions

The task system is designed to be extensible:

  • Multiple task types can coexist
  • Tasks can have priorities
  • Creatures could have different capabilities or preferences
  • Resources could require multiple creatures to move
  • Tasks could chain together (pickup -> move -> process -> store)

Collision Detection

The simulation includes basic spherical collision detection for physical interactions:

Implementation

Spherical Collision Detection: Uses distance-based collision checking

  • Each creature has a model-specific collision radius between 0.6 and 1.0 units
  • The movable block has a collision radius of 0.6 units
  • Collision detection uses simple 2D distance calculations (X and Z axes only)
  • Efficient for small populations (O(n²) is acceptable for 131 creatures)

Collision Response: Separation-based resolution

  • When creatures collide with each other, they push apart equally (50% each)
  • When creatures collide with the block, only the creature is pushed
  • Collision response applies gradual separation to prevent jittering
  • No collision occurs when a creature is carrying, picking up, dropping, or eating the block
  • This allows smooth task interactions without physics interference

Performance: Simple but effective approach

  • Direct iteration through all entity pairs
  • No spatial partitioning needed for current population size
  • Could be optimized with spatial hashing or quadtrees if population scales up
