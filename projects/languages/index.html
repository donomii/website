Languages

I keep designing programming languages. I'm not sure I can stop.

◆

Programming languages have been a side project of mine for as long as I've been writing code. Some are serious, some are deliberately broken, some are little experiments that turned into something useful at the command line. This page is a single place to keep track of them.

Throff

Throff is the big one — a dynamically typed, late binding, homoiconic, concatenative programming language. It looks Forth-ish, but the whole program (including control flow) is one big tree of words operating on a stack, and that tree can be rewritten at runtime.

There are now several implementations:

  • Original Perl interpreter
  • Go interpreter (the one most people use)
  • JavaScript port (throff-js-lib, throff-cli.js) so it runs in a browser or under Node
  • Rust port (throff-rs)
  • Jupyter kernel (throff-jupyter) — Throff in notebooks
  • Mobile builds (throffMobile, throffMobile-new) for running Throff on a phone

The combined source lives in ~/git/throff-combined and includes a VM spec, a library of examples, and the cross-platform downloads linked from the Throff project page.

Throff is the language I actually use; the others are the languages I had to write in order to figure out what I wanted Throff to be.

Linc

Linc (in ~/git/racketprogs/linc) is a linear concatenative language in the spirit of Kitten, but compiled to C.

  • Concatenative, postfix, stack-based.
  • Statically typed with row polymorphism over the stack.
  • Linear types: every value is used exactly once. clone and drop are explicit.
  • Branches are stack-neutral: condition then [ true-branch ] else [ false-branch ] if.
  • Threads can be spawned with a linear value, and typed channel endpoints (ChannelSend a, ChannelRecv a) support split / send / receive / close.

The compiler is written in C and emits C, which gets handed to a target C compiler. A --static flag asks for a single-binary native build. There's a std/ library covering math, files, paths, env, config, JSON, threads, HTTP, AWS SigV4, DynamoDB, ClickHouse — the kind of plumbing you actually need to write a useful program. The driver only links in support libraries (libcurl, OpenSSL, OpenGL, GLUT, etc.) for features the program actually uses, so simple programs stay small.

Linc is my attempt to find out whether a strict, linear, concatenative language can be pleasant to write real software in. So far: cautiously yes.

xsh

xsh (in ~/git/racketprogs/xsh) is a cross-platform shell and scripting language.

  • Homoiconic functional scripting language that works by tree reduction.
  • Specifically not Lisp.
  • Focusses on being pleasant to debug and introspect — every reduction step can be paused, inspected, and resumed.
  • Written in Go.

xsh ships as two cooperating binaries: xsh is the interpreter, and xshguardian is a sibling process the shell delegates external-program execution to, so signal handling and PTY allocation don't block the parent interpreter. There's an embedded standard library (stdlib.xsh) with map, fold, reverse, range, boolean combinators built on nand, a default prompt, and a small lined line editor with history, completions, F-keys, and Ctrl-R search.

The language has a spec and a pseudocode walkthrough of the implementation.

I want my shell to be a real programming language, and I want my programming language to be a real shell. xsh is that experiment.

Stalk

Stalk (in ~/git/racketprogs/stalk) is a small prototype-based language inspired by Smalltalk.

  • No class hierarchy. You clone existing objects.
  • No image. Source lives in plain .sta text files.
  • Simpler syntax: only message sends, lambdas, and literals.
  • Optional type annotations on lambda arguments.

Everything is a message send: methods, control flow, even object construction. A statement ends with a period; a message send is receiver name: arg name: arg. and the selector is built from the argument labels — so a familiar Smalltalk idiom like y ifTrue: [| io print: "Yes\n"] ifFalse: [| io print: "No\n"] works as you'd expect.

io print: "Hello World\n".
io println: (string join: (list 1 "a" "c")).

y = "abcde" contains: "a".
y ifTrue: [| io print: "Yes\n"] ifFalse: [| io print: "No\n"].

Stalk is what PerlTalk wanted to be, after I figured out what had gone wrong with PerlTalk.

ServiceTalk

ServiceTalk (in ~/git/racketprogs/agentic/servicetalk) is a distributed Smalltalk where every object is its own OS process, running its own HTTP server, and every message send is an HTTP RPC (fire-and-forget POST plus callback). A central coordinator handles the registry, port allocation, spawning, and the shared transcript output.

./smt coordinator          # starts everything; spawns Main by default
./smt coordinator --main "" # coordinator only, no auto-spawn

ServiceTalk classes can be written in three shapes — the runtime tries each in turn:

Shape Source Language
Dog.st Traditional Smalltalk ServiceTalk
Dog.smt S-expression (class …) ServiceTalk
Dog/ Directory, manifest + C files C (foreign)

So a familiar Smalltalk class definition just works:

class Dog [
    | name breed |

    name: n breed: b [
        name := n.
        breed := b
    ]

    bark [
        Transcript show: name , ' says: Woof!'
    ]

    name [ ^ name ]
]

…and the same class can equivalently be written as an (class …) S-expression, or as a directory of C files with a manifest if you want a foreign-class implementation that still presents as an ordinary Smalltalk object to the rest of the system. Inheritance is single-parent (class Cat extends Animal [ … ]). There are bundled foreign classes for ClickHouse, DynamoDB, S3, a Robocop-style proxy, RCounter/CCounter, and an HTTP client/server pair.

The interesting part isn't the syntax — Smalltalk is Smalltalk — it's that an object reference is literally a network endpoint, and "send a message" is literally an HTTP request. A program written in ServiceTalk is a small fleet of processes that you can scale, redeploy, or rewrite individually. There's a Docker Compose file and a Kubernetes manifest in the repo for running real fleets. A Rust port (servicetalk-rs) lives alongside the Go implementation.

ServiceTalk is what happens if you take Smalltalk's "everything is an object, everything is a message send" seriously enough to make it true at the OS level.

Atto

Atto (in ~/git/racketprogs/atto) is a minimal Lisp-shaped functional language with prefix syntax — a Go re-implementation of zesterer/atto.

fn factorial n is
    if = 0 n
        1
        * n factorial - n 1

fn main is
    print factorial 5

A program is a sequence of fn name args is body definitions. Bodies are expressions: function calls, if, integer/string/boolean/list literals, and references to bound names. Lists are cons-cell pairs. Nothing else.

I keep Atto around as a reminder of how little a real programming language can be made of.

PerlTalk

PerlTalk (in ~/git/racketprogs/PerlTalk) is a failed Smalltalk-interpreter-in-Perl experiment, plus several side projects in parser construction (BNF / PEG / ANTLR / brag).

The parser works — it can read a Smalltalk-flavoured program — but execution is incomplete: defining functions doesn't work, and trying to return from a function loops forever. The post-mortem in the repo blames an underplanned execution model and an over-ambitious nanopass-style parser ("Neo / Cell / LinkList", CellParser.pm).

The interesting stuff that came out of it:

  • peg.go + bnf/ — a Go program that loads a BNF grammar (and an input) and matches the input against a named rule, with sample grammars for BNF itself, C, Java, SQL92, and Canadian postal codes.
  • pfa/brag parsers/ — Racket brag versions of the same idea, with grammars for BNF, EBNF, JSON, and Lisp.
  • antlr/ — a small ANTLR4 Go program that prints the parse tree for any input C file.
  • perl2sxpr.pl — a Perl-source-to-S-expression converter (uses PPI), useful for staring at how Perl is actually parsed.

PerlTalk's value is mostly negative: it's the project that taught me what not to do, and that fed directly into Stalk.

Smaller language-shaped things

These aren't full languages but they live in the same headspace:

  • gom (~/git/racketprogs/gom) — Go + Macros. A preprocessor for *.gom files that applies a fixed pipeline of source rewrites and writes *.gen.go next to each input. All generated files start with the standard Code generated by gom; DO NOT EDIT. header.
  • autoparser (~/git/racketprogs/autoparser) — automatic parser-generator experiments, in the same family as the BNF / PEG / ANTLR work in PerlTalk.
  • Perl LiveObjects — a live self-modifying environment, in Perl, that's effectively a tiny language on top of Perl.

Why so many?

Each of these answers a slightly different question.

  • What if the whole program were one tree of words you could rewrite at runtime? — Throff.
  • What if every value had to be used exactly once? — Linc.
  • What if your shell were also a real programming language? — xsh.
  • What does Smalltalk look like without classes or an image? — Stalk.
  • What if Smalltalk objects were real OS processes talking over HTTP? — ServiceTalk.
  • How small can a programming language actually be? — Atto.
  • How not to write a Smalltalk interpreter? — PerlTalk.
  • Can a macro system feel native to Go? — gom.

I'll keep writing more.
